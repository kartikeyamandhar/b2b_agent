# Component 2: UI (apps/web)

Owner of: the firm console and the public claim portal. Next.js 16 App Router, React 19, TypeScript strict, Tailwind 4. Talks only to the backend API (component 1); never to the database directly. Clerk components come from component 4; Stripe elements from component 3.

Read CLAUDE.md first.

## 1. Two surfaces, one app

- Firm console at /app/... behind Clerk. Dense, operational, keyboard-friendly. The user is a compliance manager working a queue.
- Claim portal at /claim/[token]. Public, mobile-first, one claim per link, plain language, large tap targets, works on a cheap phone over bad signal. The user is a consumer holding a recalled product and a phone camera.

Design direction (load the frontend-design skill before building the first screen): no marketing gloss, no hero sections, no gradients. A government-adjacent tool that looks trustworthy and calm. One accent color for actions, one for warnings, neutral everything else. System font stack. Tables and forms do the work. Every screen has a visible state: loading, empty, error, done.

## 2. Routes

Console:
- /sign-in, /sign-up  Clerk
- /app  org switcher if the user belongs to more than one firm; otherwise redirect to /app/programs
- /app/programs  list with status, units affected, claims by status, correction rate, next MPR due
- /app/programs/new  pick a recall from the public archive (search box over GET /v1/recalls) or enter manually; shows extracted rules for review before opening; the owner edits rules inline (models, serial ranges, sold-at list, destruction instruction, value threshold)
- /app/programs/[id]  overview: funnel (issued, submitted, approved, denied, needs info, flagged, paid), cumulative corrections chart with the forecast band when available, model spend this period
- /app/programs/[id]/claims  queue: filters by status, outcome, cluster, value; sort by age; bulk approve for human-waiting claims the reviewer has inspected; row click opens the claim
- /app/claims/[id]  detail: claimant fields, photos (label, destruction, receipt) with the tool readings beside each photo, decision with cited rules, duplicate cluster members, reviewer actions (approve override, deny override, request info with a message, mark fraud), audit trail
- /app/claims/[id]/trace  the agent run: one row per step with node, tool, arguments, result, latency, cost; expandable JSON; a cost and step counter against the caps
- /app/programs/[id]/reports  MPR periods list, generate for a period, preview the boxes, download PDF, reconciliation badge
- /app/billing  plan, usage meters, Checkout and Customer Portal buttons (component 3)
- /app/settings  firm name, members and roles (Clerk organization profile embed), value threshold default, notification email

Portal:
- /claim/[token]  stepper: 1 confirm product (shows the recall title, the model list, where the label is), 2 enter model and serial or date code, 3 photos (label, then destruction if required, then receipt if required) with on-device compression and a preview, 4 purchase details (retailer from the sold-at list plus other, date), 5 payout preference (component 3 handoff), 6 review and submit
- /claim/[token]/status  current status in plain words; if needs_info, shows the question and a reply box with optional photo; if approved, shows the remedy and payout state; if denied, shows the reasons in plain language and a link to contact the firm

## 3. Data access

- Server components fetch from the API with the Clerk session token (component 4 provides a `apiFetch` helper that attaches it). Client components use @tanstack/react-query with the same helper for queue polling (every 10 seconds while the tab is visible).
- Portal pages fetch with the claim token only. No Clerk on portal routes; the Clerk middleware matcher excludes /claim/*.
- zod schemas mirror the API's pydantic schemas; generate them from the OpenAPI document (`npm run gen:api` pulls /openapi.json and writes src/lib/api-types.ts).
- Photo uploads go through the API (multipart), not directly to storage, so phash and sha256 are computed server-side and the token is checked. Client compresses images to under 1.5 MB before upload.

## 4. Components to build (in order)

1. App shell: sidebar (programs, billing, settings), org switcher, top bar with firm name and plan badge.
2. DataTable: server-driven pagination, filter chips, column sort, row selection; used by programs and claims.
3. StatusBadge and OutcomeBadge with the full status vocabulary from the backend.
4. RulesEditor: structured editor for identification_rules and remedy_rules with evidence quotes shown beside each extracted value and a "verbatim in notice" check mark.
5. ClaimDetail: three-column layout (claimant and fields, photos with readings, decision and actions).
6. TraceViewer: virtualized list of steps; each step shows node, tool, args, result, latency, cost; a header bar shows steps used of 8, cost used of 0.02 USD, elapsed of 60s.
7. Funnel and CumulativeChart: load the dataviz skill before writing either; plain line and bar, consistent palette, readable in light and dark.
8. MPRPreview: the exact boxes from the backend schema, in the order of the CPSC form, with manual-input fields editable and a reconciliation badge.
9. Portal stepper with resumable state (the token identifies the claim; partial progress is saved server-side after each step).
10. PhotoCapture: camera-first input with preview, retake, and a hint overlay ("photograph the sticker on the bottom").

## 5. State and runtime traces

Every piece of asynchronous UI state (queue polling, upload progress, resume after a reviewer action, portal step saves) ships with a written runtime trace under docs/traces/ showing the real sequence of network calls and state transitions observed in the browser, with timestamps from the network panel. No trace, not done.

## 6. Accessibility and resilience

- Portal: all form fields labeled, errors announced, works without JavaScript for the status page (server-rendered).
- Console: keyboard navigation through the queue (j, k, enter, a for approve, d for deny, i for request info, all with confirmation).
- Every API error renders a human sentence plus a correlation id from the response.
- Offline or failed upload in the portal keeps the captured photo in memory and offers retry; nothing is lost on a dropped connection.

## 7. Tests

- vitest unit tests for RulesEditor validation, StatusBadge mapping, zod parsing of API fixtures.
- Playwright: console login (Clerk test mode) -> create program from fixture recall -> open queue -> open claim -> open trace; portal full submission on a mobile viewport; portal needs_info reply. Run against the local API with the synthetic program loaded.
